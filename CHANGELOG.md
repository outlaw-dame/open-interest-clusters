# Changelog

This project is pre-1.0, so a minor version can contain breaking changes. Each release lists them under "Breaking changes" with what to do about them.

## Unreleased

### Added

- Opt-in attestation policy. Set `evidenceVerifier: { minimumAttestation: "origin" | "signature" }` on `createRecommendationOnboardingLifecycle` and every reported event, plan member consent and curated-set provenance entry is accepted only if an issued attestation passed in the new optional `attestations` field of `reportCandidateEvents`, `assessPlan` or `refresh` covers it (same content digest, subject, kind and exact source ids, fresh, strong enough). Anything else is refused with the usual `RecommendationEvidenceVerificationError` (`rejected`, fixed message with no subject or content), before anything is stored or cleared. It is off by default because no adapter issues attestations yet, so without the setting nothing changes and results still say `unverified`. `verifier` becomes optional when the setting is used, and if given it must accept too. Also adds `minimumAttestationAuthority`, `attestationMaxAgeMs`, `recommendationEvidenceAttestationSourceIds`, `normalizeRecommendationEvidenceVerificationOptions`, `assertRecommendationEvidenceAttestationList` and an optional `attestations` field on the verifier context. Existing callers are unaffected.
- `verifyRecommendationAtprotoLabelSignature` checks that a labeler signed a `com.atproto.label.defs#label`. You pass the label, the labeler's current DID document and a clock string. It finds the `#atproto_label` Multikey (secp256k1 or P-256, compressed only), encodes the label as canonical DAG-CBOR with a small built-in encoder, and verifies the 64 byte signature over its SHA-256, rejecting high-S signatures as ATProto requires. It returns `{ verified: true, keyType, negated, hasExpiry }` or `{ verified: false, reason }` with a fixed reason and never throws. Expired labels return `expired`, signed negations come back with `negated: true`, and there is no fallback to the repo signing key. It uses only `node:crypto`, so no dependency was added, and nothing in the core path calls it. The encoder is checked against `@ipld/dag-cbor` output and the signatures against `@atproto/crypto`. Also exports `encodeRecommendationAtprotoLabelForSigning` and `isRecommendationAtprotoLabelTimestamp`. Repo/MST/CAR proofs and ActivityPub signatures are still not verified, see `docs/atproto-label-verification.md`. A label dated more than five minutes after `now` is refused with `future_label`. A positive result does not show that the labeler has not since signed a negation, so check for a newer `neg` label yourself.
- Optional `subjectLock` on `createRecommendationOnboardingLifecycle`. You give it `acquire(subjectId, { signal })` that resolves to a release function (Web Locks, a database advisory lock, and so on). The lifecycle takes it after the per-subject queue and holds it around `applySelection`, `withdrawSelections`, `reportCandidateEvents`, `assessPlan` and `refresh`. A failed, timed out or aborted acquire rejects with `RecommendationSubjectLockError` before anything is written. The release always runs, a failing release never changes the result and goes to `onReleaseError`. Waits are bounded by `timeoutMs` (default 5 s, at most 60 s). Without the option nothing changes, and the library still gives no cross-process guarantee of its own. Also exports `RecommendationSubjectLock`, `RecommendationSubjectLockOptions`, `RecommendationSubjectLockRelease`, `RecommendationSubjectLockFailureReason` and the two timeout constants.
- `subjectLock` gains a hold deadline. `maxHoldMs` (default 60 s, at most 300 s) limits how long the work may run under the lock, and `onHoldExceeded` is told once when it passes. At the deadline the library aborts a signal that is passed to the evidence verifier (`context.signal`), to `firstSession.execute` (`request.signal`, combined with the caller's; with no `subjectLock` it gets the caller's signal as given, or none) and to the event store retry loops, and it stops starting new steps. It does not release the lock at the deadline. The lock and the per-subject queues are held until the work has settled, and then the call fails with `RecommendationSubjectLockError` reason `hold_exceeded`, which has no `cause` and never contains the subject ID. Work that ignores the abort and never settles keeps the lock held, and `onHoldExceeded` is the only notice, so wire it up. Exports `RECOMMENDATION_SUBJECT_LOCK_DEFAULT_HOLD_MS` and `RECOMMENDATION_SUBJECT_LOCK_MAX_HOLD_MS`. `subjectLock` is not in a released version, so no released API changes.
- `diffRecommendationCuratedAccountSet` compares the last snapshot of a curated account set with a fresh read and returns lifecycle events ready for `reportCandidateEvents` (set deleted, no longer discoverable, now sensitive, member revoked, rejected or removed). The fresh read is a union of `found`, `not_found` and `unknown`, so a transport error is never mistaken for a deletion. It only ever reports changes that make a plan less usable, and throws on mismatched provider or set ID, backwards `observedAt`, oversized sets or malformed input. Also adds `createRecommendationCuratedAccountSetMemberCandidateId` and `MAX_RECOMMENDATION_CURATED_ACCOUNT_SET_MEMBERS`. The report also has `noLongerAcceptedCandidateIds` for members who went from accepted to pending or unknown, which have no event kind. Exclude those IDs on the next `refresh`.
- `createRecommendationAtprotoLabelAttestation` issues an `atproto_label_signature` evidence attestation (authority `protocol_native`, proof class `signature`) only when a label's signature verifies. Signed negations and expired labels are refused, and a failed check returns a fixed reason and issues nothing. The optional `maxLabelAgeMs` refuses a label whose `cts` is older than that (`label_too_old`), which gives a label with no `exp` an upper bound.
- Attestations can bind evidence content. A `contentDigest` (from `recommendationEvidenceContentDigest`) is now required on every attestation, for every mechanism, and an optional `expiresAt` is available. `createRecommendationEvidenceAttestation` throws without a digest, the verifier always hashes the evidence it receives and refuses a mismatch (`digest_mismatch`), and `evaluateRecommendationEvidenceAttestation` throws if the requirement has no digest. There is no `bindContent` option, and passing one throws. New rejection reasons are `attestation_expired` and `digest_mismatch`. Attestation code is not in a released version, so no released API changes. The docs explain how to compute the digest for an HTTPS origin read. Byte arrays are encoded as `bytes("<base64>")`, so they never share a digest with a plain object like `{ $bytes: "..." }`.
- Evidence attestations. `createRecommendationEvidenceAttestation` records that a check ran (subject, source ids, kind, mechanism, authority from the provider-discovery vocabulary, time). `createRecommendationAttestationEvidenceVerifier` plugs into the existing `evidenceVerifier` hook and says `verified` only for an attestation issued by that function that matches the subject, kind and source ids, is fresh (default 15 minutes) and strong enough. Origin-only evidence such as a Mastodon Collection read is an `origin` attestation and is refused wherever a `signature` proof is required. No protocol signature is verified by the library and no dependency was added. `recommendationProviderDiscoveryAuthorityAtLeast` compares authorities.
- `checkRecommendationCandidateEventStoreCompareAndSet(store)`. It tests a store's `supportsCompareAndSet` claim by trying a stale write on a throwaway probe subject, and returns `passed`, `failed` (with a fixed reason) or `inconclusive` when the store threw. The onboarding lifecycle runs it once before its first guarded write, and fails the write if the check cannot finish.
- `candidateEvents.setExclusionRetentionMs` on `createRecommendationOnboardingLifecycle`, and `MAX_RECOMMENDATION_CANDIDATE_SET_EXCLUSION_RETENTION_MS` (365 days). It lets set-level events outlive ordinary ones so a hidden set stays hidden longer. It defaults to `retentionMs`, so nothing changes unless you set it, and it may not be shorter than `retentionMs`. Deletion and revoked consent still clear these events immediately.

- `transitionRecommendationProfilePersistence` can now move stored candidate events along with the profile. Give both locations a `candidateEventStore` (and optionally `candidateEventLimits`). Events are copied, read back, and deleted from the source before the source profile is removed, with the same consent check, backoff and rerun behavior as the profile. The result gains an optional `candidateEvents` field (`moved`, `nothing_to_move` or `skipped_store_missing`). Callers that pass no event store see no change.
- A private ATProto space on the user's own PDS can hold interests like a pod. This is evidence and policy only. The library ships no spaces adapter and cannot see what an adapter writes. New values: source visibility `atproto_private_space`, access basis `atproto_space_authority` and preference storage target `atproto_private_space`. Onboarding with that target labels the signals `server_allowed` and gives them ATProto evidence, and the signal policy accepts that evidence (user-owned, server-side consent) with the existing `signal.allow.user_controlled_remote` reason. A store that holds the profile or candidate events in a space is declared `user_owned` + `server_allowed` and used through the `user_pod` target, so the same consent and relabelling apply. There is no target, visibility or access basis that accepts a public repo, so public repo evidence is never accepted as a placement for private interests. Spaces give access control, not confidentiality: the ATProto team's [alpha announcement](https://atproto.com/blog/atproto-spaces-alpha) says space data is not encrypted and is readable by any user or application with access. It does not say whether the PDS host can read it, and we assume it can. That post also warns that the alpha code had no careful security review and not to upload sensitive information. The [public beta post](https://atproto.com/blog/getting-ready-for-the-spaces-public-beta) says spaces moves from alpha to public beta with the reference PDS release of December 1. Check the current status before relying on spaces. The library expects the user's own DID to be the space authority but cannot check it, so your adapter has to. The union types `RecommendationSourceVisibility`, `RecommendationAccessBasis` and `RecommendationPreferenceStorageTarget` each gained a member, so an exhaustive `switch` over them in your code needs a new case (see "Breaking changes").
- Optional `publiclyReadable` on the storage adapter manifest. A remote user-owned store sets it to `true` if anyone can read it without the user's permission, such as a public ATProto repo. `true` is refused for subject-level state on every path that checks the manifest (profile read and write, the candidate event store, and the profile move) with the new reason `state.deny.publicly_readable_store`. A value that is not a boolean is rejected. Leaving it out changes nothing. The library cannot verify the declaration, so `false` or an absent field is not evidence the store is private.
- `lifecycle.refresh` now returns the evidence label the report result already had: `evidenceVerification`, `verifierId`, `verifiedKinds` and `storedEventsNotChecked`. It reflects what this refresh checked, including the attestation policy. Events reported with the refresh are covered. Stored events that were not reported in this call are counted as not checked, so a plain rerun says `unverified` and a mix says `partial`. The fields are optional on `RecommendationOnboardingRefreshResultWithSetExclusions`, and `RecommendationOnboardingRefreshResult` is unchanged.

### Changed

- A one-off error while the lifecycle checks a store's compare-and-set claim no longer sends that write out without `expectedDigest`. The check is retried with the same backoff as other store calls, and if it still cannot finish the report fails with nothing written. Only a definite `failed` answer falls back to the per-subject queue. An unfinished check is not remembered, so the next write checks again.
- `transitionRecommendationProfilePersistence` no longer drops older candidate events when you leave out `candidateEventLimits`. It used to read the source with the default 30 day window, so a set-level exclusion the lifecycle keeps for longer (`setExclusionRetentionMs`) was left out of the copy and then deleted with the source. Unset limits now default to the widest the lifecycle allows (90 days for events, 365 for set-level exclusions), and the lifecycle applies its own limits on its next read. Limits you pass still narrow the move. This only affects the event move added in this release.
- `transitionRecommendationProfilePersistence` now runs the compare-and-set conformance check on the destination event store before it sends `expectedDigest`, like the lifecycle does. A store that lies gets a plain write (the move already holds both stores' queues). A check that hits a store error is retried with the move's backoff and then fails the move with the source left in place. The profile and event placement checks now share one internal rule, so they cannot drift apart. The check writes and deletes an empty record under a random probe subject on the destination store.
- A candidate event store that declares `supportsCompareAndSet` but accepts stale writes (or refuses current ones) is no longer trusted. The lifecycle falls back to its per-subject queue without `expectedDigest`, the same as a store that never declared support. Before this, a store that lied let two devices overwrite each other without any signal.
- A lifecycle with `candidateEvents: { store }` built on the library's own derived-state orchestrator now clears the stored events on `derived.deleteSubject` without any extra wiring. The delete is part of the durable `candidate_cache` deletion step, so a failure is reported as pending and retried on the next call. If you already wrap an invalidator with `createRecommendationCandidateEventDeletionInvalidator`, that store is not deleted twice. A custom or wrapped `derived` port still needs the helper.
- `derived.deleteSubject` no longer races a report that is saving candidate events. Store saves and deletes share a per-subject queue keyed by the store object, so the deletion waits for the save and then clears it. Previously the save could land after the deletion and a second deletion was needed. This holds within one process using one store object.
- The candidate event store now keeps one slot per set, kind and candidate ID for set-level events (`set_deleted`, `set_not_discoverable`, `set_sensitive`). Reporting the same set again with a later time replaces the earlier event instead of adding another, so repeated reports cannot fill the cap. At the cap a report for a new set still fails and nothing is evicted. Records written earlier that hold duplicates are tidied on the next save.

### Breaking changes

- **Interests kept in a user pod are now labelled `server_allowed`.** Before, a profile stored in a pod (ActivityPods or Solid) kept `local_only` labels. A pod is a server, even a user-controlled one, so the label now says where the interests are processed: `local_only` on the device, `server_allowed` in a user-owned server store. Provider-owned and shared-operator stores are still refused for subject-level state. What changes:
  - `bootstrapRecommendationProfileFromOnboarding` with `storageTarget: "user_pod"` defaults to `privacyBoundary: "server_allowed"` and throws a `TypeError` for an explicit `local_only`. On the device the default stays `local_only`, and an explicit `server_allowed` throws. `createRecommendationOnboardingProfileSeed` and `lifecycle.applySelection` do the same for a selection stored in `activitypods_pod`, `solid_pod` or `atproto_private_space` (explicit `local_only` throws) and for a `local_app` selection (explicit `server_allowed` throws). They use ActivityPods ACL evidence for a pod, which is the evidence the signal policy accepts for `server_allowed`. The device-side throw is new here: before, the seed let an explicit `server_allowed` for a `local_app` selection through, and only a profile store with a signal policy refused it later, so a seed built with a custom store that did not check could succeed. `encrypted_sync` and `provider_storage` selections are not covered by this check and are still refused by the signal policy.
  - `writeRecommendationProfileStoreRecordSafely` relabels `local_only` entries to `server_allowed` when the target is `user_pod`, and `server_allowed` entries to `local_only` when the target is `local_app`, the same as the transition does. It throws a `TypeError` for a `privacyBoundary` that does not fit the target. A device write needs no consent, because the label only gets stricter. `aggregate_only` entries are still refused on both targets.
  - `transitionRecommendationProfilePersistence` relabels for the destination (pod: `server_allowed`, device: `local_only`), after the consent check and before the copy is written. It still copies, reads back and deletes the source last. A destination already in place with the wrong label is relabelled in place on the next run. A `privacyBoundary` option that does not fit the destination throws.
  - Candidate events carry no label, so nothing about them is relabelled. They move into a store whose placement matches the destination, as before.
  - Moving to a pod needs the user's server-side consent for the data use. Without it, or with revoked, deleted or mismatched consent, nothing is written or relabelled.
- **Three unions gained members.** `RecommendationSourceVisibility` (`atproto_private_space`), `RecommendationAccessBasis` (`atproto_space_authority`) and `RecommendationPreferenceStorageTarget` (`atproto_private_space`) are wider. Code that switches on them and relies on the compiler to prove every case is covered fails to compile. Add a case for each new member. For a `default` branch, pick the least trusting treatment: treat an unknown visibility or access basis as not allowed, and an unknown storage target as not a place for subject-level state.
- **Migration.** Remove any `privacyBoundary: "local_only"` you pass with `user_pod`, or change it to `"server_allowed"`, and make sure the consent policy allows server-side use (`serverSideDataUses`) for the data use. Profiles already in a pod as `local_only` need no migration step. They still load as stored, and the next write to the pod or the next `transitionRecommendationProfilePersistence` relabels them `server_allowed`. If you want them healed sooner, call the transition or a write once. Code that reads `privacyBoundaries` from a pod profile and expects `local_only` must accept `server_allowed`. If you derive signals yourself and keep a ledger of them, note that the label is part of a signal's content, so a selection moved to a pod produces signals with a different digest than before.

### Documented

- What `local_only` and `server_allowed` mean, and which store each fits. See "Breaking changes". Interests are matched against the user's own profile, and remote servers are only asked to check candidates and updates. A private ATProto space on the user's own PDS is documented as an allowed placement under the same conditions as a pod, and a public repo as never allowed (see "Added"). New tests cover every persistence path, the candidate event store, the profile move, and the requests the source and discovery clients build.
- Several processes and scheduled refresh: the library never refreshes on its own (the application calls `refresh`) and cannot lock across processes without shared storage. The Phase 7 doc now explains why there is no built-in lease and gives a concrete lock recipe with expiry, crash recovery and backoff.
- `lifecycle.refresh` can return fewer than `limit` recommendations when the first-session object ignores `excludeSourceIds` and had already cut its list to `limit`. The refresh filter only removes and does not rerun the first session. The library's own orchestrator is not affected.

## 0.3.0

Changes from PR #136, on top of 0.2.0.

### Added

- Set-level exclusion on refresh. When you report `set_deleted`, `set_not_discoverable` or `set_sensitive`, `lifecycle.refresh` passes the set's source ID to the first session as `excludeSourceIds`. Candidate generation drops every candidate whose provenance includes it, before ranking and before the candidate cap, so no candidate ID is needed. `excludeSourceIds` is also accepted on the first-session request directly.
- One onboarding queue per engine. Lifecycles built on the same engine now queue behind each other instead of racing. If the signal ledger moves underneath a write, the write is replanned against the new state. Unrelated ledger errors are not retried.
- An opt-in candidate event store. Pass `candidateEvents: { store }` to `createRecommendationOnboardingLifecycle` and reported events are kept, so `assessPlan` and `refresh` still honor them after a restart. Without it nothing is stored, as before. It comes with a new state domain, `candidate_lifecycle_events` (device-owned and user-owned placements only), an in-memory reference store, `createRecommendationCandidateEventDeletionInvalidator`, and the lifecycle methods `listReportedCandidateEvents` and `assessPlan`. When a store is configured, reporting events needs a consent `policy`.
- An evidence verifier hook. Apps can plug in a verifier that checks reported events and the consent evidence on a plan. A verifier can only make a plan less usable. If it rejects, throws, times out or returns junk, the report or assessment is blocked.
- Extension interfaces `RecommendationEngineEventHistoryReader` (`readEventHistory`) and `RecommendationCandidateStateInvalidator` (`invalidateCandidateState`). The factories return the richer types `RecommendationEngineOrchestratorWithHistory` and `RecommendationDerivedStateInvalidationOrchestratorWithCandidateState`. If you pass the lifecycle an engine or derived-state port that lacks the method, it checks at runtime and throws a `TypeError` on the first call that needs it, not when the lifecycle is created. Selection changes and event reports fail before the ledger or the event store is written. The one exception is a `consent_revoked` withdrawal, which still deletes stored candidate events before it reports the missing `readEventHistory`.
- `tests/public-api-surface.test.ts`, which pins exported names and interface member lists against `tests/fixtures/public-api-surface.json`.

### Changed

- `readEventHistory` is no longer a required member of `RecommendationEngineOrchestrator`, and `invalidateCandidateState` is no longer a required member of `RecommendationDerivedStateInvalidationOrchestrator`. Both were required in 0.2.0. Code that implements these interfaces (wrappers, test doubles) compiles again without them. Code that calls the two methods through the base types stops compiling, see "Breaking changes".
- The new lifecycle members and result fields live on extending types instead of the 0.2.0 ones. `createRecommendationOnboardingLifecycle` returns `RecommendationOnboardingLifecycleWithCandidateEvents` (adds `listReportedCandidateEvents` and `assessPlan`). `reportCandidateEvents` returns `RecommendationOnboardingCandidateReportResultWithEvidence`, `assessPlan` and the assessment functions return `RecommendationCandidatePlanAssessmentWithEvidence` (both add `evidenceVerification`, `verifierId`, `verifiedKinds` and `storedEventsNotChecked`), and `refresh` returns `RecommendationOnboardingRefreshResultWithSetExclusions` (adds `excludedSetSourceIds`). `RecommendationOnboardingLifecycle`, `RecommendationCandidatePlanAssessment`, `RecommendationOnboardingCandidateReportResult` and `RecommendationOnboardingRefreshResult` keep their 0.2.0 members, and the extended types are assignable to them. Hand-written doubles and hand-built values still compile.

### Breaking changes

Two, both type-level. Nothing changes at runtime.

- `RECOMMENDATION_STATE_DOMAINS` and `RecommendationStateDomain` gained `candidate_lifecycle_events`. An exhaustive `switch` or `Record<RecommendationStateDomain, ...>` will not compile until it handles the new value. Give those branches a default that treats an unknown domain as the least trusting one. The old union could not be kept, because this is a real domain that the placement policy and the candidate event store use, and a union without it would be wrong about what they return.
- Calling `readEventHistory` on a value typed `RecommendationEngineOrchestrator`, or `invalidateCandidateState` on a value typed `RecommendationDerivedStateInvalidationOrchestrator`, fails with TS2339, because both methods moved to extension types. Type the value as what the factory returns (`RecommendationEngineOrchestratorWithHistory`, `RecommendationDerivedStateInvalidationOrchestratorWithCandidateState`) or let inference do it. Making the methods optional on the base types would keep the call compiling but force an `undefined` check at every call site, so it would still break callers, and it would hide that a plain implementer may lack them.

Not breaking: the consent `policy` input is only needed when a candidate event store is configured. `RecommendationCandidateEventStore.save` takes an optional third argument and the interface gains the optional `supportsCompareAndSet`.

### Upgrade order

A derived-state task saved with `candidate_state_changed` is rejected by versions before 0.2.0 (`Invalid recommendation derived-state invalidation reason.`). Upgrade readers before writers. Stored candidate event records carry a `schemaVersion`, and a reader that meets a newer one throws instead of guessing.

## 0.2.0

Covers PRs #128 to #135. Phase 6 follow-ups and Phase 7 (onboarding lifecycle).

### Breaking changes

- **New required members on the engine and derived-state orchestrators.** `RecommendationEngineOrchestrator` gained `readEventHistory(subjectId)`, and `RecommendationDerivedStateInvalidationOrchestrator` gained `invalidateCandidateState({ subjectId, occurredAt? })`. Anything you implement by hand has to add them. (Relaxed again in Unreleased.)
- **Wider invalidation reason union.** `RECOMMENDATION_DERIVED_STATE_INVALIDATION_REASONS` gained `candidate_state_changed`. Exhaustive switches over it need a new case.
- **`collections` is now `communities`.** The provider capability that gates community candidates was renamed because it collided with Mastodon Collections. There is no alias. A descriptor or observation that still says `collections` is treated as an unknown capability, so normalization throws `Invalid recommendation provider capability observation.` Report `communities` instead.
- **`starterPackMembers` takes wrappers.** Each member is now `{ eligibility, consent }` instead of a bare eligibility result, and consent must show an accepted membership. Plans built without `starterPackMembers` throw, and a member whose consent is not `accepted` is rejected. Wrap each member and supply consent evidence.
- **Starter-pack member candidates need `curated_account_set` provenance.** When building a starter-pack plan, each member candidate must carry a `curated_account_set` provenance entry whose source ID (set provider and set ID), observation time and item ID match the member's consent. Otherwise plan building throws `Recommendation starter-pack member consent must match curated-set provenance on the candidate.` Make sure your source attaches it.
- **Curated-set source emits `starter_pack` candidates.** When a caller asks for the `starter_pack` kind, the curated account set source now returns the set itself as a candidate, gated by the `starter_packs` capability. Callers that assumed only members would come back need to handle the new kind.

### Added

- The start-of-lifecycle APIs: `createRecommendationOnboardingLifecycle` with selection edit, remove, rerun and withdrawal (`source_retracted`, `consent_revoked`), candidate lifecycle assessment of action plans against reported events, and a crash-safe profile move between device-owned and user-owned storage.
- Starter-pack plans bind each member to the resolved account identity from its eligibility result.
- Backoff waits can be aborted, and lifecycle times that run more than five minutes ahead of the clock are rejected with a `RangeError`.
- The engine and invalidation orchestrators share one keyed serializer.

See `docs/phase7-onboarding-lifecycle.md` for the lifecycle and `docs/recommendation-provider-discovery.md` for the capability rename.
